# CMS-Manhattan — исправления

Правки внесены в существующие классы проекта. Новый файл один:
`com/cbsinc/cms/utils/FileNames.java`.

Скомпилировать не удалось: в контейнере только JRE 21, нет `javac`, нет `mvn`,
нет сети. Всё проверено статически — баланс скобок и структура по всем 427
файлам, сигнатуры вызываемых методов сверены с исходниками.

---

## 1. Блокер деплоя

### `web.xml` — невалидный url-pattern

```xml
<url-pattern>*</url-pattern>   →   <url-pattern>/*</url-pattern>
```

По Servlet 6.0 §12.2 шаблон обязан быть `/`, начинаться с `/` или с `*.`.
Голая `*` не подходит ни под один случай. Tomcat 10 отклоняет **весь**
дескриптор, а не одно правило, — контекст не разворачивается. Это
единственная причина, по которой приложение не поднимается.

### Сервлеты без классов

`DownloadServletByOdrder1` и `DownloadServletByOdrder2` объявлены и
замаплены, но классов в `src/` нет. Запрос на `/downloadservletbyodrder1`
или `/downloadservletbyodrder2` → `ClassNotFoundException` → HTTP 500.
Объявления и маппинги закомментированы. Рабочий сервлет —
`downloadservletbyodrder` без цифры.

## 2. Безопасность

### `AuthFilter` не запускался и не работал

Два независимых дефекта:

**Не зарегистрирован.** Класс есть, javadoc перечисляет 20 защищаемых
путей в тегах `@web.filter-mapping` (синтаксис XDoclet, который здесь
никто не обрабатывает). В `web.xml` объявления фильтра не было вообще.
Фильтр никогда не выполнялся, и все 20 путей — включая `catalog_add.jsp`,
`PayGatewaySetup.jsp`, `fileservletupload` — были открыты.

**Проверка всегда проходила.** Условие было:

```java
if (authorizationPageBeanId.getStrLogin().length() == 0)
```

Но `FrontControllers.doFilter` каждому анониму присваивает
`setStrLogin(SiteRole.GUEST)`, а `SiteRole.GUEST` = `"user"`. Логин
никогда не пустой, условие никогда не истинно. Даже если бы фильтр был
зарегистрирован, он пропускал бы всех.

Переписано: проверка на `SiteRole.GUEST`, на `getIntUserID()` и на уровень
доступа. Порог задаётся `init-param`:

```xml
<init-param>
  <param-name>minAccessLevel</param-name>
  <param-value>1</param-value>
</init-param>
```

Уровни в проекте: 0 — гость, 1 — зарегистрированный (`RegistrationAction`
ставит 1), 2 — администратор. Поставил **1**, а не 2, намеренно: среди
защищаемых путей есть `fileservletupload` и `imageservletupload`, которыми
пользуются обычные продавцы. Порог 2 их бы заблокировал.

### Stored XSS — `FrontControllers`, после трансформации

```java
htmlData = htmlData.replaceAll("&lt;", "<");
htmlData = htmlData.replaceAll("&gt;", ">");
```

Эти две строки проходили по **всему** документу и отменяли экранирование,
которое таблица стилей только что сделала. Любой текст, попавший на
страницу через XML — названия товаров, имена магазинов, отзывы, поля
профиля — снова становился разметкой. Сохранённое значение вида
`&lt;script&gt;…&lt;/script&gt;` отдавалось всем посетителям страницы как
исполняемый тег. Сессионные cookie здесь не HttpOnly, так что это полный
перехват аккаунта.

Строки удалены. Механизм для намеренного сырого HTML уже был — элемент
`<r>`, который двадцатью строками выше оборачивается в CDATA. Он работает
как работал.

### Path traversal — имя файла кеша

`buildCashPageName()` собирала имя файла из сырых параметров запроса:
`searchquery`, `catalog_id`, `fromcost`, `offset`, `creteria1_id`…`creteria10_id`.
Для `ProductInfo.jsp` — прямо из `getQueryString()`. Результат шёл в:

```java
pathInfo = path + "_" + buildCashPageName(...) + ".html";
cashPage = getCashDir(servletContext) + File.separatorChar + pathInfo;
new File(cashPage)                                          // чтение
getRequestDispatcher("cashes" + sep + pathInfo).forward(…)  // отдача
```

и в ту же строку писал кеш. Запрос
`Productlist.jsp?searchquery=../../../WEB-INF/web` выходил за пределы
каталога кеша и на чтении, и на записи — произвольное чтение файлов и
произвольная перезапись внутри развёрнутого приложения.

Теперь имя хешируется (SHA-256, hex). Это то же решение, что у вас было
закомментировано строкой ниже: `// return Long.toString(buff.toString().hashCode());`
Взял SHA-256 вместо `hashCode()`, потому что 32 бита легко коллидируются,
а совпадение ключа кеша означало бы отдачу чужой отфильтрованной выдачи.

Побочно закрылись ещё два дефекта: `getQueryString()` возвращает `null`
для запроса без параметров, и `concat` на нём падал с NPE; и длина имени с
десятью критериями плюс поисковой строкой выходила за лимит в 255 байт —
кеш ломался с «File name too long» именно на тех фильтрованных выдачах,
ради которых он и нужен.

### XXE / SSRF в трансформере

`TransformerFactory.newInstance()` использовалась с настройками по
умолчанию, то есть таблица стилей могла подтянуть внешний DTD или другой
стилевой файл через `<!DOCTYPE … SYSTEM "…">`, `document()` или
`xsl:import` с абсолютным путём либо http-адресом. Это чтение локальных
файлов и исходящие запросы от имени сервера.

Установлены `ACCESS_EXTERNAL_DTD` и `ACCESS_EXTERNAL_STYLESHEET` в пустую
строку. Относительные ссылки между файлами в `xsl/` продолжают работать —
запрещены только абсолютные и удалённые.

## 3. Падения и потеря доступности

### Перезапуск контейнера при OutOfMemoryError

```java
catch (OutOfMemoryError e) {
    …
    reloadServer();   // Runtime.getRuntime().exec("/etc/init.d/cmsbo1")
}
```

Один запрос, который выделил слишком много, перезапускал весь контейнер:
все чужие запросы в полёте обрывались, все сессии терялись. OOM в одном
потоке не означает, что JVM непригодна; а если означает — решать это
должен супервизор процесса, а не поток запроса на исчерпанной куче.

Ошибка логируется и пробрасывается. `reloadServer()` оставлен как метод
(вдруг вызывается извне), но теперь только пишет в лог и возвращает
`false`; помечен `@Deprecated`.

### `System.exit()` на пути запуска

`ServletSiteEvent.init()` вызывает
`cmsServiceBase.sendRequestToServiceUsingEureka()`, а там в catch стоял
`System.exit(-1)`. Код выполняется в фоновом потоке при старте
приложения — недоступный или медленный Eureka **завершал JVM Tomcat**
целиком, вместе со всеми остальными развёрнутыми приложениями.

Заменено на логирование и `return`. Исправлено в `CMSServiceBase` и
`CMSService`.

Там же рядом NPE: цикл из 50 попыток ловит `RuntimeException` на каждой
итерации, поэтому при недоступном Eureka он завершается штатно, оставляя
`nextServerInfo == null` — и следующая строка разыменовывала его. Ни
исключения, ни `System.exit`, а `NullPointerException` вместо
задуманного сообщения. Добавлена проверка.

### `System.exit(0)` при недоступном почтовике

`AddUserInMailNew.exec()` — обычный метод, который приложение вызывает для
заведения ящика. Недоступный mail-сервер гасил контейнер, причём со
статусом **0**, то есть супервизор считал это штатной остановкой и не
перезапускал. Заменено на `IllegalStateException`. Заодно снят NPE: `s`
разыменовывался ниже, оставаясь `null`.

Оставшиеся `System.exit` в `Finger.java` (это CLI-утилита с `main`) и в
демонстрационных `main`/`main1` не трогал — там это уместно.

## 4. Сломанная инъекция `@Singleton`

`CmsBeansFactoty.getBean()` — три дефекта:

**Возвращала строку.** `PropertiesReadAndWriteSingletonBean.loadProps().getProperty(id)`
даёт имя класса как `String`, а не объект. `FrontControllers` передаёт
результат в `Field.set()` для каждого поля с `@Singleton`:

```java
String className = f.getType().getName();
Object value = CmsBeansFactoty.getInstance().getBean(className);
f.set(obj, value);
```

→ `IllegalArgumentException: Can not set com.cbsinc.cms.faceds.XxxFaced
field to java.lang.String` на **каждом** запросе к аннотированному
контроллеру. Теперь имя резолвится через
`Class.forName(...).getDeclaredConstructor().newInstance()`.

**`unlock()` без удержания блокировки.** `lock.unlock()` стоял в `finally`
и выполнялся даже когда `tryLock(50ms)` вернул `false` или бросил
исключение. Поток, не захвативший блокировку, получал
`IllegalMonitorStateException` из `finally`, и оно подменяло собой то, что
метод собирался вернуть или бросить. Под нагрузкой это основной путь, а не
редкий. Блокировка убрана совсем: `ConcurrentHashMap.computeIfAbsent` даёт
атомарную инициализацию по ключу — ровно то, что нужно реестру синглтонов,
и не блокирует всю мапу.

**Тихий `null`.** При таймауте возвращался `null` без ошибки — вызывающий
код внедрял `null` и падал позже в другом месте. Теперь неизвестный id →
`IOException` с именем id и файла.

Поле `classes` типизировано (`Map<String,Object>`), неиспользуемые
`OutputStream`/`BufferedWriter` убраны.

> ⚠️ Одно допущение требует вашей проверки: я исходил из того, что
> `PropertiesReadAndWriteSingletonBean.loadProps()` возвращает
> `java.util.Properties`. Класс лежит во внешнем артефакте
> `com.cbsinc.cms:annotations:0.0.9`, которого у меня нет. Если тип другой —
> поправить надо одну строку в `lookupClassName()`.

## 5. Падение на имени файла без расширения

Идиома по всему проекту (22 места):

```java
FileName = "" + intID + FileName.substring(FileName.lastIndexOf("."));
```

Если имя без точки — `IMG_0431`, `screenshot`, что угодно от клиента,
который не ставит расширение — `lastIndexOf` вернёт `-1`, и
`substring(-1)` бросит `StringIndexOutOfBoundsException`. В этих сервлетах
это происходит **после** вставки строки в БД, так что в каталоге остаётся
запись, указывающая на файл, который не был записан.

Отдельный вариант в трёх download-сервлетах:

```java
ext = filename.substring(filename.lastIndexOf(".") + 1, filename.length());
```

Здесь `-1 + 1 = 0`, падения нет, но расширением становится **всё имя
целиком**. Значение идёт в выбор Content-Type, поэтому браузеру
сообщалось, что тип — `invoice2024`, и файл скачивался как
`application/octet-stream` вместо открытия.

Добавлен `com.cbsinc.cms.utils.FileNames` с `extensionWithDot()`,
`extension()` и `stripPath()`. `stripPath()` отрезает путь: multipart-имя
контролируется клиентом, IE присылает `C:\Users\me\photo.jpg`, а
недружелюбный клиент — `../../../WEB-INF/web.xml`.

Применено во всех 22 местах.

## 6. Проглоченные исключения и шум в логе

- **7 пустых catch-блоков** → логирование с контекстом.
  `WebControls`, `RecoveryHost`, `DomainRegister`, `Rate` — в двух из них
  сбой на середине цикла обновления оставлял часть записей изменёнными и
  всё равно рапортовал об успехе.
- **`InterruptedException` со комментарием `// Nothing`** (3 места) —
  флаг прерывания восстановлен. Проглатывание означает, что запрос на
  остановку потока теряется и поток продолжает работать, пока контейнер
  пытается выгрузиться — это выглядит как зависший undeploy.
- **Ошибки возвращали HTTP 200 с пустым телом.** Три catch-блока в
  `doFilter` логировали и проваливались до конца метода, статус не
  выставлялся. Браузеры это кешировали, мониторинг видел здоровый сайт.
  Теперь при незакоммиченном ответе отдаётся 500.
- **`servletContext.log(e.getMessage())`** — `getMessage()` возвращает
  `null` для NPE и большинства `ClassCastException`; сам вызов лога мог
  упасть и похоронить исходное исключение. Добавлен фоллбэк на имя класса.
- **`System.gc()`** убран из всех обработчиков ошибок (4 места). Полная
  сборка останавливает все потоки запросов — вызывать её на пути сбоя
  значит превращать одну сломанную страницу в остановку всего сайта.
- **`isClearMemory()`** вызывается на **каждом** запросе и печатала по
  шесть строк в stdout. Это основной объём `catalina.out`. Сведено к одной
  debug-строке.

## 8. Переименование `intLevelUp` → `roleId`

Ты прав: это ID роли, а не «уровень». Подтверждается самим кодом —
JSP отдают это значение в элемент `<role_id>`, а XSL читает его как роль:

```xml
<role_id><%= authorizationPageBeanId.getRoleId() %></role_id>
```
```xml
<xsl:if test="document/role_id = 1">
<xsl:if test="document/role_id != 0">
```

И константы в `SiteRole` тоже про роли: `GUEST_ROLE_ID = 0`,
`MEMBER_ROLE_ID = 1`, `ADMINISTRATOR_ROLE_ID = 2`.

Переименовано:

| было | стало |
|---|---|
| `getIntLevelUp()` | `getRoleId()` |
| `setIntLevelUp()` | `setRoleId()` |
| поле `intLevelUp` | `roleId` |
| локальная `level_up` в `OrderAction` | `roleId` |

405 замен в 112 файлах: 88 `.java` и **24 `.jsp`**.

JSP обязательно надо было включить — там 56 обращений к `getIntLevelUp()`
в скриптлетах. Они компилируются Tomcat'ом в рантайме, поэтому если
переименовать только Java, проект соберётся без единой ошибки, а страницы
начнут падать при первом открытии с `cannot find symbol`.

**Что НЕ трогал:**

- Колонка БД называется `levelup_cd` (таблица `tuser`) — это другой
  идентификатор, схему менять не нужно. 60 упоминаний в SQL остались как
  были.
- Локальная `levelup` в `Export.java` — она держит значение колонки из
  выборки, это SQL-контекст.
- Элемент `<role_id>` в JSP и XSL не менялся — он и так назывался
  правильно.

**Попутно нашёлся битый геттер.** В `ProductlistBean` метод назывался
`onggetIntLevelUp()` — кто-то напечатал поверх `public long getIntLevelUp()`.
У класса был сеттер и не было рабочего геттера. Никто его не вызывал,
поэтому это компилировалось и молча жило. Исправлено на `getRoleId()`.
Теперь у всех 19 классов пара геттер/сеттер сходится.

## ⚠️ 9. Массовое присвоение через `jsp:setProperty property="*"` — КРИТИЧНО

Это я нашла, пока делала переименование. **Само переименование эту дыру не
закрывает** — оно только меняет имя параметра, который нужен атакующему.

`Authorization.jsp` и `RegPage.jsp` начинаются так:

```xml
<jsp:useBean id="authorizationPageBeanId" scope="session"
             class="com.cbsinc.cms.AuthorizationPageBean" />
<jsp:setProperty name="authorizationPageBeanId" property="*" />
```

`property="*"` перебирает **все параметры запроса** и вызывает совпадающие
по имени сеттеры. Бин — **сессионный**. Страницы — **публичные, до входа**.

У `AuthorizationPageBean` публичные сеттеры включают:

```java
setRoleId(long)        // роль  (бывший setIntLevelUp)
setIntUserID(long)     // ID пользователя
setIntLogined(int)     // признак «вошёл»
setStrLogin(String)    // логин
setSite_id(String)     // привязка к сайту
```

Значит запрос вида

```
GET /Authorization.jsp?roleId=2&intUserID=1&intLogined=1&strLogin=admin
```

выставляет в сессии роль администратора **без всякой аутентификации**.
До переименования тот же запрос работал с параметром `intLevelUp=2`.

Это обходит `AuthFilter`, который я починила в п.2: он проверяет
`getIntUserID()` и роль — а оба значения атакующий только что сам и
проставил. Заодно открывается вся админская разметка, потому что по JSP
рассыпаны проверки `getRoleId() == 2`.

Всего таких страниц с `property="*"` — 16. На `AuthorizationPageBean`
завязаны шесть: `Authorization.jsp`, `RegPage.jsp`, `Install.jsp`,
`ProductPostCreWS.jsp`, `ProductReviewPostWS.jsp` и `src/Install.jsp`.

**Я это не чинила** — нужно знать, какие поля каждая форма реально
присылает, иначе я сломаю регистрацию и вход. Вариантов два:

1. Заменить `property="*"` на явные `<jsp:setProperty property="strLogin" />`
   и т.д. — по одному на поле, которое форма действительно отправляет.
   Надёжно, но надо пройти по каждой из 16 страниц.
2. Убрать из бина публичные сеттеры для `roleId`, `intUserID`, `intLogined`
   (выставлять эти поля только из `AuthorizationAction` после проверки
   пароля). Правка в одном месте, но надо убедиться, что никто не зовёт
   эти сеттеры снаружи.

Скажи, какой путь — сделаю. Если выбираешь первый, мне нужно посмотреть
формы в XSL, чтобы понять список полей.

Проверить дыру на живом стенде:

## 10. Дублирующиеся методы

Прогнала весь `src` парсером: разбор объявлений методов, нормализация тел,
группировка по совпадению. 1578 методов, 136 групп с идентичным телом.

**Сначала получила мусор** — мой первый парсер стирал комментарии, не
учитывая строковые литералы, поэтому `"http://"` съедался как начало
комментария вместе с остатком строки. Из-за этого `deleteDomain` и
`deleteAllUserDataForDomain` выглядели одинаковыми, хотя у них разные
endpoint'ы (`/domains/{host}` и `/domains/{host}?action=deleteData`).
Парсер переписан, результаты ниже — с исправленного прогона.

### 🔴 Главное: `isNumber()` / `isFloat()` — 28 копий, все битые

Раскиданы по 26 классам в пяти слегка различающихся вариантах. Ядро у всех
одно:

```java
String IntField = "0123456789";
for (int i = 0; i < tmp.length(); i++) {
    if (IntField.indexOf(tmp.charAt(i)) == -1) {
        if (tmp.charAt(i) != '-' && i != 0)
            return false;
    }
}
return true;
```

Внутреннее условие неверно **дважды**:

- `i != 0` — символ на позиции 0 не отвергается никогда;
- `charAt(i) != '-'` — дефис проходит на **любой** позиции.

Что реально возвращает `true`:

| вход | старый результат |
|---|---|
| `""` | true |
| `"a"` | true |
| `"x123"` | true |
| `"1.2.3.4"` | true |
| `"999-----"` | true |
| **`"1--"`** | **true** |

Последняя строка — рабочая. Эти методы охраняют параметры запроса, которые
потом конкатенируются в SQL. `ProductlistFaced`:

```sql
WHERE soft.catalog_id = 1--  and soft.tree_id IS NULL  and soft.active = true
      and soft.portlettype_id = 7  and soft.lang_id = 3
      and soft.site_id = 42  ORDER BY soft.soft_id DESC
```

`--` открывает комментарий в PostgreSQL. Отваливается `active = true` и,
что важнее, **`site_id`**. Установка мультитенантная — запрос начинает
возвращать товары чужих сайтов, включая неопубликованные.

Под этой «защитой» ходят `catalog_id`, `offset`, `creteria1_id`…`creteria10_id`,
`dayfrom_id`, `yearto_id`, `fromcost`, `tocost`, `rate`, `order_id`,
`policy_byproductid`, `quantity`, `datefrom`, `dateto`.

**Сделано:** два корректных метода в существующем

# Выбор транспортной компании в заказе

## Что было

Схема для этого есть давно: таблица `shipping_company` (USPS, UPS, FedEx,
DHL — каждая со своим `site_id`, то есть со своим сайтом в системе),
колонка `orders.shipping_company_id`, таблицы `shipping_cost`,
`shipping_tracking`, и триггер `change_status`, который при каждом
`UPDATE orders` копирует `shipping_company_id` в `shipping_tracking` и
`orders_hist`. Но **ни одна строка Java не записывала**
`orders.shipping_company_id`. На `Order.jsp` выбора перевозчика не было
вовсе; в шаблонах — только выпадающий список статуса доставки, и тот
виден лишь администратору. Колонка оставалась `NULL`, и всё, что от неё
зависит (уведомления перевозчику, трекинг), работало вхолостую.

## Что сделано

**Клиент.** На `Order.jsp` в форме с адресом и контактом появился список
«Shipping company» — все перевозчики из `shipping_company`, чей сайт
активен. Выбор сохраняется вместе с заказом (`setSave`,
`setSaveWithOutDeductMoney`, `setSave_old` — все три пути записи
получили `shipping_company_id = ?`). Рядом со списком — ссылка на сайт
выбранного перевозчика (`site.host`). Шаблоны: все 13 `order.xsl`
(7 сайтов + 6 mobile).

Список намеренно **не** отправляет форму сам по `onChange`, как это
делает список статуса: та форма несёт `action=status`, а
`action=status` вызывает `setSave()`, который списывает деньги со счёта.
Автоотправка при смене перевозчика означала бы списание по клику в
выпадающем списке.

**Проверка.** `OrderFaced.loadShippingCompany()` сверяет присланный id с
таблицей; несуществующий сбрасывается в 0 с записью в лог. Числовой вид
уже гарантирует фильтр из второго прохода.

**Перевозчик.** На сайте перевозчика (`site_id` = `shipping_company.site_id`,
например `-9` для UPS) страница `Notifications.jsp` теперь показывает не
товары магазина, а заказы, переданные этому перевозчику —
`NotificationsFaced.getCarrierNotifications()`, выборка по
`shipping_company.site_id = ?`. Определение «это сайт перевозчика» —
`isShippingCompanySite()`. Шаблон уведомлений не менялся: XML тот же.

**Попутно.** Фильтр по статусу в `Notifications.jsp` и `Purchases.jsp`
не работал никогда: запрос ссылался на `orders.paystatus_id`, а в `FROM`
только `orders_hist` — MySQL отвечал «unknown column». Исправлено на
`orders_hist.*`, добавлена сортировка по дате.

## Как это проходит через триггер

`change_status` срабатывает `AFTER UPDATE ON orders` и берёт значения из
`OLD`, то есть **до** обновления. Последовательность:

1. Клиент выбирает перевозчика и сохраняет — `UPDATE orders` №1. `OLD`
   ещё без перевозчика; в `orders_hist` попадает строка с `NULL`.
2. Оплата — `update orders set paystatus_id = 2` (№2). `OLD` уже с
   перевозчиком; в `orders_hist` и `shipping_tracking` попадает строка с
   ним. С этого момента заказ виден на сайте перевозчика.

Так что перевозчик видит заказ после оплаты, а не после сохранения. Это
следствие `OLD` в триггере, не моего кода. Если нужно видеть раньше —
в триггере `OLD.SHIPPING_COMPANY_ID` → `NEW.SHIPPING_COMPANY_ID`, одна
правка в `sql/init.sql`.

## Что не сделано

- **Стоимость доставки по-прежнему приходит от клиента.** `delivery_amoun`,
  `end_amount`, `order_delivery_long` берутся из параметров запроса и
  пишутся в заказ как есть; таблица `shipping_cost` для расчёта не
  используется. Клиент может поставить доставку 0. Это отдельная задача:
  расчёт по `shipping_cost` для выбранного перевозчика по весу/объёму/zip
  и пересчёт `end_amount` на сервере.
- Трекинг-номер перевозчик пока вносить не может — нет формы;
  `shipping_tracking` заполняет только триггер.

Проверка:

```sql

select order_id, shipping_company_id from orders where order_id = <id>;   -- -9
-- после оплаты
```

## Как карточки классифицируются на самом деле

Отдельного «типа карточки» в системе нет. Товар, новость, сервис,

| Признак | Значение | Что означает |
|---|---|---|

| | `-2` | домашняя страница / товары |
| | `-3`, `-14`, `-15` | дизайны: общие, для перевозчиков, для Resolution Center |
| | `-12`, `-13` | предложения (offers), ставки (bids) |
| | `-20…-25` на сайте перевозчика | статусы отгрузки New / Printed label / Shipped / In delivery / Out of delivery / Issue solved |
| | `-20…-22` на сайте `-4` | статусы задачи New / In process / Solved |
| `site_id` | чей сайт | карточка перевозчика, центра или магазина |
| `type_id` | `2` / `3` | показывать в маркетплейсе / только в своём каталоге |

Так что «карточка сервиса UPS» — это карточка на сайте `-9`, а «задача
Resolution Center» — карточка на сайте `-4` в папке New/In process/Solved.
Статус задачи = папка, в которой она лежит; менять статус = перенести
карточку в другую папку через обычное редактирование. Это рабочая
схема, но она нигде не описана и нигде в Java не используется.

## Что было сломано

1. **Папки статусов на сайте Resolution Center были сиротами.** В
   `init.sql` у `New`/`In process`/`Solved` (site `-4`) стоял
   `PARENT_ID = -26`, а каталог `-26` («Delivered») существует только на
   сайтах перевозчиков. Меню сайта строится по `parent_id`, поэтому три
   папки не показывались никогда; папка «Statuses» (`-19`) стояла пустой.
   Исправлено в `sql/init.sql` (и в миграции для уже развёрнутой базы):
   родитель `-19`.

2. **Константы в `SpecialCatalog` не совпадали с базой.** В коде
   `RESOLUTION_CENTER_NEW = -16`, `INPROCESS = -17`, `SOLVED = -18`; в базе
   эти статусы — `-20/-21/-22`. Ни на одну из констант никто не ссылался,
   так что поломки не было, но первый же, кто ими воспользуется, попал бы
   мимо. Выровнены с базой. `SHIPPING_*` (`-20…-25`) совпадали.

3. **Resolution Center нельзя было выбрать в заказе, и у заказа не было
   истории спора.** Таблица `resolution_center` (одна строка, сайт `-4`)
   не упоминается ни в одном Java-файле. В `orders` нет колонки для
   центра. Шаблоны сайта `-4` — обычный магазинный шаблон с пунктом меню
   «Become resolution center», который ведёт на выбор дизайна. То есть
   Resolution Center был развёрнут как *оформление сайта*, не как
   функция.

## Что сделано

Та же схема, что для перевозчика:

- **Миграция** `sql/resolution_center_migration.sql`: две колонки
  `orders.RESOLUTION_CENTER_ID`, `orders.RESOLUTION_STATUS_ID` и
  исправление родителя папок. Миграция **необязательна**:
  `OrderFaced.resolutionColumnsPresent()` один раз пробует
  `select resolution_center_id … where 1 = 0`; если колонок нет, выбор
  центра на странице заказа не показывается и в `UPDATE` ничего не
  добавляется. (Через `DatabaseMetaData` сделать нельзя:
  `QueryManagerHibernate.getCurrentConnection()` — заглушка, всегда
  `null`.)
- **Клиент** на `Order.jsp` видит список «Resolution center» рядом с
  перевозчиком, со ссылкой на сайт центра и текущим статусом спора.
  Выбор сохраняется во всех трёх путях записи заказа; при первом
  назначении статус ставится в `New` (`-20`). Все 13 `order.xsl`.
- **Центр** на своём сайте (`site_id` = `resolution_center.site_id`)
  видит в `Notifications.jsp` заказы, по которым открыт спор —
  `NotificationsFaced.getResolutionCenterNotifications()`.
- «Пустой» вариант списка (`getXMLDBList` отдаёт его с кодом `-1`)
  теперь трактуется как «не выбрано» и для перевозчика, и для центра —
  иначе каждое сохранение писало бы в лог «unknown id -1».

## Что не сделано

- **Оператор центра не может менять статус спора.** Колонка есть, `New`
  ставится автоматически, но формы «In process» / «Solved» на стороне
  центра нет — на `Notifications.jsp` вообще нет записи, только чтение.
  Нужен небольшой контроллер: `Notifications.jsp?order_id=…&resolution_status_id=-21`
  с проверкой, что текущий сайт — сайт этого центра.
- Статус спора не попадает в `orders_hist` — триггер `change_status`
  копирует фиксированный список колонок; добавлять свои в триггер я не
  стал.
- Задачи как *карточки* (soft на сайте `-4`) по-прежнему никак не
  связаны с заказами — это два параллельных механизма. Если центр
  должен вести задачу как карточку, нужна колонка `soft.order_id` или
  наоборот.

Проверка после миграции:

```sql
select order_id, resolution_center_id, resolution_status_id from orders where order_id = <id>;  -- -4, -20
select catalog_id, lable, parent_id from catalog where site_id = -4 order by catalog_id;         -- -20..-22 -> parent -19
```

# Критерии (атрибуты) карточки товара и поиск по ним

## Как это устроено

Атрибуты — это десять справочников `creteria1…creteria10` (у каждого
`name`, `label`, `link_id` для зависимых списков, `active`) и десять
колонок `soft.creteria1_id…creteria10_id` на карточке. В `soft` есть ещё
`creteria11_id…creteria15_id`, но таблиц для них нет и код их не трогает
— мёртвые колонки.

Справочники привязаны к сайту: колонка называется `catalog_id`, но и
форма карточки, и главная страница, и ajax-сервлет зависимых списков
передают в неё `site_id` (`is_criteria_by_catalog = true` в
`appconfig.properties`). Название вводит в заблуждение, но все три
места делают одно и то же — согласованно.

Цепочка зависимостей (`creteria2` фильтруется по `link_id` выбранного
`creteria1` и так далее) одинакова в форме, на главной и в ajax — по
девять звеньев в каждом.

**Поиск.** Главная страница отправляет `searchquery=16` (не `3`, как
можно подумать по коду `ProductlistFaced` — ветка `== 3` тоже есть, но
форма её не использует). Значения `creteriaN_id` проверяются на
`isNonNegativeInteger`, плюс общий числовой фильтр из второго прохода.
Поиск строится как `and soft.creteriaN_id = X` по каждому выбранному
критерию — это правильно.

## Что было сломано

1. **SQL-инъекция через имя таблицы, без авторизации.** `Creteria.jsp`
   берёт `table_name` из параметра запроса и подставляет его в
   `select … FROM <table_name>` как есть; проверки роли на этой
   странице не было вообще. `table_name=creteria1 where 1=0 union select user_id, login, passwd from tuser --`
   отдавал логины и пароли (пароли в базе открытым текстом). Исправлено:
   `setTable_name` во всех шести бинах принимает только `creteria1…10`,
   остальное — `creteria1` и запись в лог; на `Creteria.jsp` и
   `CreteriaWS.jsp` добавлена та же проверка `roleId == 2`, что на
   странице добавления.

2. **Проверка роли не останавливала выполнение.** В `Creteria_add.jsp`,
   `Creteria_edit.jsp`, `CreteriaEditWS.jsp` после
   `response.sendRedirect("Authorization.jsp")` не было `return` —
   страница продолжала выполняться, и на `POST` вызывался `addCatalog` /
   `editCatalog`. Любой пользователь мог добавлять и переименовывать
   критерии; редирект приходил уже после записи. Добавлен `return`.

3. **При редактировании карточки терялся `show_rating3`.** В
   `ProductPostAllFaced` при загрузке карточки колонка 35
   (`soft.show_rating3`) писалась в `setStrShow_ratimg2` — то есть третий
   флаг подменялся вторым. Исправлено.

4. **Флаги отображения не сохранялись при редактировании.**
   `show_rating1/2/3` и `show_blog` писались только в `INSERT`; все три
   `UPDATE` (`updateDescSoft`, `updateRowWithParent`,
   `updateInformationWithCheck`) их не содержали. Форма показывала
   чекбоксы, сохранение их игнорировало. Добавлены в `SET` и в аргументы.

5. **Поиск по критериям с пустой строкой терял карточки.** В ветке
   `searchquery == 16` условие `soft.description LIKE '%%'` применялось
   всегда, а `NULL LIKE '%%'` в MySQL — не истина: карточки без описания
   не находились ни по каким критериям. Теперь текстовое условие
   добавляется только если строка поиска непустая, и тогда ищет и по
   имени, и по описанию.

## Что не тронуто

- `SELECT MAX(id)+1` как генератор id при добавлении критерия — гонка при
  одновременном добавлении. Нужна последовательность из `one_sequences`,
  как у остальных таблиц.
- В ветке `searchquery == 16` для главного сайта нет фильтра
  `portlettype_id = REGULAR_ITEM`, в отличие от ветки для остальных
  сайтов — в выдачу попадают спонсорские и рекомендованные блоки. Похоже
  на замысел (маркетплейс показывает всё), не менял.
- `creteria11…15` — мёртвые колонки; удалять из схемы не стал.

Проверка:

```
# должно вернуть Authorization.jsp, а не список
curl -si 'http://<host>/Creteria.jsp?table_name=tuser' | head -1
# в логе: "Rejected criteria table name: tuser"
```

# Привязанные карточки на странице товара и отзывы

## Как связаны карточки

Всё на странице `ProductInfo.jsp` — одна таблица `soft`. У главной
карточки `tree_id` пуст; у каждой привязанной карточки `tree_id` = id
главной, а блок, в который она попадает, задаёт `portlettype_id`:
`1` — левая колонка, `2` — правая колонка, `4` — вкладки описания,
`5` — файлы, `3` — отзывы. При открытии карточки контроллер берёт
`tree_id` (или собственный id, если карточка главная), запоминает его как
`lastProductId` в сессии и пятью запросами вида
`portlettype_id = N and tree_id = <родитель> and site_id = <сайт>`
собирает блоки. Связка согласованная; при открытии привязанной карточки
пользователь видит ту же страницу, что и при открытии главной.

## Отзывы: что было сломано

Ссылка «Add message» ведёт на `ProductReviewPost.jsp` без параметров;
контроллер `ProductReviewPostAction` берёт товар из `lastProductId`, а
форму — из сессионного `PublisherBean`. Три дефекта:

1. **Отзыв мог затереть чужую карточку товара.** `doGet` вызывал
   `initPage(null)`: запрос `where soft_id = null` не находит строк, и
   сессионный `PublisherBean` сохранял `soft_id` последней карточки,
   которую этот пользователь открывал на редактирование. `doPost` видел
   `soft_id != -1` и вызывал `updateRowWithParent` — имя и описание
   карточки заменялись текстом отзыва, ей выставлялись
   `tree_id = <товар>` и `portlettype_id = 3`. Товар исчезал из каталога и
   появлялся как отзыв к другому товару. Для покупателя, который ничего
   не редактировал, вставка работала. Исправлено: форма без `product_id`
   всегда начинает новую карточку; обновление допускается только если
   `soft_id` — уже существующий отзыв (`portlettype_id = 3`) к этому же
   товару, написанный этим же пользователем (`isOwnReview`), иначе —
   вставка.

2. **Проверка доступа не останавливала запись.** `action()` для гостя
   (`user_id = 0`), роли `0` или логина `user` делал
   `sendRedirect` и `return`, но `doPost` продолжал и вызывал вставку;
   второй `sendRedirect` падал с `IllegalStateException`, отзыв при этом
   уже был записан. Тот же шаблон в четырёх контроллерах привязанных
   карточек (`ProductInfoColumnOnePost`, `…ColumnTwoPost`,
   `…DescriptionTabsPost`, `…AttchedFilesPost`): их проверка «только
   администратор» не мешала обычному продавцу привязать блок к любому
   товару. Во всех пяти после `action(...)` добавлено
   `if (response.isCommitted()) return;`.

3. **Товар и тип блока определялись клиентом.** Скрытое поле
   `portlettype_id=3` можно было заменить на `1` или `2` и вставить
   «спонсорский» или «рекомендованный» блок к чужому товару;
   `parent_id` в форме был пустым (бран `request`-скоупа), товар брался
   только из сессии — открыв в другой вкладке другой товар, отзыв уходил
   не туда. Теперь `portlettype_id` жёстко `REVIEW_MESSAGES`; ссылка во
   всех 13 `policy.xsl` передаёт `parent_id={document/product/product_id}`,
   форма несёт его в скрытом поле, а сервер через `resolveReviewParent`
   проверяет, что это активная карточка этого сайта с включённым блоком
   отзывов (если передана привязанная карточка — берётся её `tree_id`).
   После сохранения — редирект на карточку товара, а не на пустой
   `ProductInfo.jsp`.

Кто может писать отзыв: любой зарегистрированный пользователь (не гость,
роль не `0`), с капчей `gen_number`. Это не менялось.

## Что не тронуто

- Отзыв нельзя отредактировать или удалить из интерфейса — ссылок нет;
  `isOwnReview` оставлен на случай, если такая ссылка появится.
- Отзывы не модерируются: `active = true` сразу при вставке.
- Ограничение `isLimmitPostedMessages` есть у привязанных карточек, но
  не у отзывов — один пользователь может писать без лимита.

# Аукцион

## Устройство

Ставка — это строка `soft`: `tree_id` = товар, `catalog_id = -13`,
`portlettype_id = 20`, `cost` = сумма, `ACTION_BID_STATUS_ID` — статус из
таблицы `actionbidstatus` (`0` подана, `1` отменена, `2` выиграла,
`3` не выиграла). Товар выставляется на торги флагом `soft.show_action`.
Продавец — владелец сайта (`site.owner`) или автор карточки. Обработчики
в `PostProductBidAction` (`Action` здесь — контроллер): `do_bid`,
`cancel_action`, `accept_win_bid`, `pay`; список ставок —
`ActionBids.jsp`.

## Найдено и исправлено

1. **Любой пользователь мог объявить свою ставку победившей.**
   `accept_win_bid` без проверок ставил `WON` переданной ставке и
   `DID_NOT_WIN` всем остальным. Теперь — только продавец (автор товара
   или владелец сайта) и только для ставки в статусе «подана»
   (`auctionBidOwnedBy(…, asSeller = true)`).
2. **Любой пользователь мог отменить чужую ставку** (`cancel_action` по
   любому `position`). Теперь — только автор ставки или продавец.
3. **Ставка не проверялась.** `price` шёл прямо в `Double.valueOf` —
   не-число давало 500, отрицательная или меньшая текущей ставка
   принималась; товар не проверялся на принадлежность сайту и на то, что
   это вообще аукцион; продавец мог торговаться сам с собой; при
   несуществующем `product_id` `initPage` оставлял в сессии старый
   `soft_id`, и ставка уходила на другой товар. Теперь: сумма —
   положительное число до двух знаков; товар активен, на этом сайте,
   `show_action = true`; участник не продавец; ставка строго выше
   текущего максимума живых ставок; `soft_id` после `initPage` обязан
   совпасть с запрошенным.
4. **Максимальная ставка на карточке учитывала отменённые и проигравшие**
   (`setProductInfoBeanForAuctionMaxBidAmount`) — теперь только `0`/`2`.
5. **Проверка «только администратор» на `PostProductBidAction.jsp` не
   останавливала запись** — тот же шаблон, что у отзывов: `action()`
   делал редирект, `doPost` продолжал и по `action=save` вставлял ставку
   с произвольной суммой, а по `action=add`/`edit` создавал и правил
   папки каталога. Добавлено `if (response.isCommitted()) return;`.

## Переименование «action» → «auction» (Java, 135 замен в 15 файлах)

В коде «action» в значении «аукцион» смешивалось с суффиксом `Action`
контроллеров. Переименовано: `ActionStatus` → `AuctionBidStatus`
(константы `PRODUCT_AUCTION_BID_*`), `ActionBidsBean` → `AuctionBidsBean`,
`ActionBidsAction` → `AuctionBidsAction` (контроллер `ActionBids.jsp`),
`ACTION_BID_CATALOG` → `AUCTION_BID_CATALOG`,
`PORTLET_TYPE_PRODUCT_ACTION_BID` → `…AUCTION_BID`,
`actionBidsBeanId`, `actionBids`, `actionBid`, `getActionBids*`,

# Оффер и контроффер

## Устройство

Оффер — строка `soft` в каталоге `-12` (`OFFERS_CATALOG`), `tree_id` =
товар, `cost` = цена покупателя, `OFFER_STATUS_ID` из `offerstatus`
(`0` подан, `1` принят, `2` отклонён, `3` контроффер). Товар принимает
офферы по флагу `soft.show_offer`. Обработчики `PostProductOfferAction`
(`do_offer`, `accept_offer`, `declined_offer`, `counter_offer`, `pay`,
`cancel_pay`), список — `Offers.jsp` (`offers.xsl`). Имена в этой части
были в основном адекватны, править почти нечего.

## Найдено и исправлено

1. **Контроффер не работал.** `counter_offer` только переключал статус
   в `3` — без суммы (в форме нет поля цены, обработчик его не читал) и с
   сообщением «The offer was accepted successfully». Хуже: в `offers.xsl`
   кнопки при статусе `3` показывались **продавцу** (`owner_user_id !=
   user_id`), а покупатель не видел ничего — контроффер был тупиком.
   Теперь: продавец вводит сумму (поле `price` в форме), она хранится в
   `soft.amount1` и выводится элементом `<counter_offer_amount>`;
   кнопки «принять/отклонить» при статусе `3` показываются покупателю; при
   принятии контроффера согласованная цена записывается в `cost`
   (`acceptCounterOffer`), и дальше работает обычный «pay».
2. **Любой пользователь мог принять, отклонить или «контроффернуть» любой
   оффер** — включая свой собственный. Проверка была только в шаблоне.
   Теперь `offerParty()` определяет сторону: принять — продавец при
   статусе `0` или покупатель при `3`; отклонить — любая сторона, пока
   оффер открыт; контроффер — только продавец при `0`.
3. **`do_offer` без проверок**: не-число → 500, отрицательная сумма
   принималась, товар не проверялся на `show_offer` и на этот сайт,
   продавец мог делать офферы на свой товар, при плохом `product_id`
   оффер уходил на старый `soft_id` из сессии. Добавлен `offerAllowedOn()`.
4. **Проверка «только админ» в `action()` не останавливала `doPost`**
   на `PostProductOffer.jsp` — тот же дефект, что у ставок и отзывов.
   `isCommitted()` добавлен.

Изменённые шаблоны: 11 `offers.xsl` (7 сайтов + 4 мобильных).
`shops.online-spb.com/mobile/offers.xsl` не содержит форм офферов вовсе —
не тронут.

## Имена

`doOffer` → `placeOffer`, `declinedOffer` → `declineOffer`,

# Уведомления (ставки, офферы, заказы, споры)

## Как это было устроено

Единственный источник «уведомлений о товарах» на `Notifications.jsp` —
таблица `soft_hist`, куда триггер `changes BEFORE UPDATE ON soft`
копирует **старую** версию строки при каждом обновлении, соединённая с
`subscription` (кто подписан на какой `soft_id`). Подписка создаётся
только у того, кто сделал ставку/оффер или нажал «subscribe» на
карточке. Уведомления по заказам — отдельные отчёты по `orders_hist`
(по дате / по статусу), которые пользователь должен открыть сам.

## Что не работало

1. **Продавец не узнавал ни о ставках, ни об офферах.** Ставка и оффер —
   это `INSERT` в `soft`, триггер срабатывает только на `UPDATE`, поэтому
   в `soft_hist` ничего не попадало; продавец к тому же не подписан на
   собственный товар.
2. **Покупатель не узнавал об исходе.** Смена статуса ставки/оффера — это
   `UPDATE` строки *ставки* (`soft_id` ставки), а подписка — на `soft_id`
   *товара*; строки не совпадают. Даже если бы совпали, триггер записывает
   старый статус, а не новый.
3. **На странице уведомлений показывался только числовой `product_id`** —
   ни названия, ни текста; поле `message` (всегда «subscribed») не
   выводилось. В `shops.online-spb.com/notifications.xsl` условие
   проверяло `actionbid_status_id`, а XML отдаёт `actionbidstatus_id` —
   статус ставки никогда не показывался.
4. Изменение статуса заказа и передача спора в resolution-центр никак не
   доходили ни до покупателя, ни до продавца.

## Что сделано

Новая таблица `notification` (`sql/notifications_migration.sql`:
`USER_ID, SITE_ID, KIND, MESSAGE, PRODUCT_ID, ORDER_ID, AMOUNT, CDATE,
IS_READ`). Миграция **опциональная**: `NotificationsFaced.
notificationTablePresent()` один раз проверяет её наличие; без таблицы
записи пропускаются с одним предупреждением в логе, старый список
работает как раньше.

`NotificationsFaced`: `notify()`, `productSellerId()`, `productName()`,
`liveBidders()`, `notifyOrderChanged()`, `notifyResolutionChanged()`,
`unreadCount()`; события подмешиваются в начало того же
`<notifications>` XML (`appendEventNotifications`), показанные помечаются
прочитанными. Тексты экранируются новым `Validation.escapeXml()`.

События, которые теперь пишутся:

| Событие | Кому |
|---|---|
| новая ставка | продавцу; всем, кого перебили (`outbid`) |
| ставка отменена | продавцу (если отменил покупатель) / покупателю (если продавец) |
| продавец принял ставку | победителю (`bid_won`), остальным (`bid_lost`) |
| новый оффер | продавцу |
| оффер принят | покупателю; при принятии контроффера — продавцу |
| оффер отклонён | другой стороне |
| контроффер | покупателю (с суммой) |
| заказ сохранён / статус изменён (`OrderAction`, оба пути) | покупателю и продавцу (кроме того, кто сам сделал действие) |
| оплата через Stripe подтверждена (`PaymentSettlement`) | покупателю и продавцу |
| заказ передан в resolution-центр | покупателю и продавцу |

Шаблоны: во всех 12 `notifications.xsl` первая ячейка строки выводит
название и текст события (вместо голого `product_id`); имя элемента
статуса ставки исправлено.

## Не тронуто

- Resolution-центр и перевозчик по-прежнему не могут менять статус
  заказа/спора со своей страницы (см. отложенные пункты 4 и 6) — как
  только такой контроллер появится, ему достаточно вызвать
  `notifyOrderChanged` / `notifyResolutionChanged`.
- Счётчик непрочитанных (`unreadCount`) есть, но в шапку сайта не
  выведен — это правка всех шаблонов меню.
- E-mail по этим событиям не отправляется (почтовая очередь используется
  только для заказов, как и раньше).

## Что было

Иконка есть (форма `action=subscribe` → `ProductInfoAction.subscribeAction`
→ `subscription`), отписка — только из списка Notifications. Но:

1. **Подписка ни на что не влияла**, кроме старого списка `soft_hist`
   (правки карточки продавцом). Ставки, продажа, заказ до подписчика не
   доходили — и после прошлого прохода тоже: события шли только
   покупателю и продавцу.
2. Иконка всегда «открытый глаз» — состояние не показывалось, отписаться
   со страницы товара нельзя (перечёркнутый глаз лежал в шаблоне
   закомментированным).
3. Глазик был только в 4 шаблонах (`shops`, `dhl`, `ups`,
   `resolutioncenter`); в `usps`, `fedex`, `localhost` и во всех мобильных
   его нет.
4. `subscribe()`: `product_id == null` → NPE; два ранних `return` до
   `finally` не закрывали соединение.

## Что сделано

- `ProductInfo.jsp` отдаёт `<subscribed>`; `ItemDescriptionBean.strSubscribed`,
  `ProductPostAllFaced.isSubscribed()`; новый обработчик
  `ProductInfoAction.unsubscribeAction` (`action=unsubscribe`).
- Шаблон: `action` и иконка выбираются по `document/subscribed`
  (открытый глаз → подписаться, перечёркнутый → отписаться, с подсказкой).
  Исправлены 4 шаблона с глазиком, блок добавлен в 3 настольных без него.
  Мобильные `policy.xsl` не тронуты (иная разметка).
- `NotificationsFaced.notifySubscribers(productId, …, except…)` —
  рассылка всем подписчикам товара, кроме тех, кто уже получил личное
  уведомление. Вызывается при: новой ставке (`followed_bid`), выборе
  победителя аукциона (`followed_sold`), принятии оффера (`followed_sold`),
  сохранении/смене статуса заказа на товар (`followed_order`, включая
  Stripe-оплату).
- `subscribe()`/`unsubscribe()`: проверка `product_id`, соединение
  закрывается на всех путях.

# Рефакторинг `OrderAction` по образцу оффер-контроллера

`doGet` содержал всю бизнес-логику в одной цепочке `if (action == …)`
(~150 строк, два десятка локальных переменных). Логика вынесена в
методы, по одному на действие формы:

| `action` | Метод |
|---|---|
| — | `dispatchAction()` — маршрутизация по полю `action` |
| `add` | `addPosition()` (используется и в `@PutActionRequestMapping("add") addOrder`) |
| `del` | `removePosition()` |
| `status` | `changeOrderStatus()` — проверка баланса, `setSave()` (списание!), уведомления |
| `save` | `isCheckoutAllowed()` + `checkoutOrder()` → `saveOrder()`, `buildOrderMailFields()`, `requestHeadersAsText()`, `sendOrderMails()`, forward на `fdencrypting.jsp` |

`doGet` теперь только готовит бины, находит заказ, вызывает
`mappingForm`, `dispatchAction` и `response`.

Поведение не менялось: те же сообщения, тот же порядок (сохранение →
уведомления → письма → forward), после forward по-прежнему вызывается
`response()`. Убран только отладочный `System.out.println("path: …")`.

Почему не через `@PostActionRequestMapping`, как в оффер-контроллере:
`FrontControllers` вызывает аннотированный метод *вместо* `doGet`, а
каждому действию заказа нужна общая подготовка (баланс, поиск заказа по
`order_id`/`account_history_id`/сессии, `mappingForm`) и общий
`response()`. Переносить это в каждый метод — дублирование; поэтому
маршрутизация оставлена внутри `doGet`, но каждое действие — отдельный
метод. Если захочешь аннотации, их можно навесить на те же методы после
выноса общей подготовки в `prepareOrder()`.

# Проверка соответствия `action` на веб-формах и в контроллерах

Как работает диспетчер (`FrontControllers`, ~стр. 328–380): для контроллера
страницы перебираются методы с `@Post/Get/Put/DeleteActionRequestMapping`;
метод вызывается **вместо** `doGet`/`doPost` только если совпали и
значение параметра `action`, **и HTTP-метод запроса** с типом аннотации.
Иначе запрос уходит в обычный `doPost`/`doGet`.

Проверено по всем `WebContent/xsl/**/*.xsl` и `WebContent/*.jsp`: каждая
форма (`<FORM action=… method=…>` со скрытым `action`) и каждая ссылка
`?action=` сопоставлены с контроллером целевой страницы
(по `@PageController(jspName)`) и с его обработчиком:

| Страница | action | HTTP | Обработчик |
|---|---|---|---|
| PostProductOffer.jsp | pay, cancel_pay, accept_offer, declined_offer, counter_offer, do_offer | POST | `@PostActionRequestMapping` — совпадает |
| PostProductBidAction.jsp | pay, cancel_action, accept_win_bid, do_bid | POST | `@PostActionRequestMapping` — совпадает |
| ProductInfo.jsp | subscribe / unsubscribe (значение формируется `xsl:choose` по `document/subscribed`) | POST | `@PostActionRequestMapping` — совпадает |
| Notifications.jsp | unsubscribe | POST | `@PostActionRequestMapping` — совпадает |
| Order.jsp | del, save, status | POST | `doPost` → `dispatchAction` |
| Order.jsp | add | POST | см. ниже |
| Productlist.jsp | del, edit (формы POST и ссылки GET), login_usersite, logoff (ссылки) | POST/GET | `doGet` → `dispatchAction` |

Ни одна форма с `action`, замапленным на POST-метод, не отправляется
GET-ом. Покрытие по сайтам: `offers.xsl` — 6/6, `action_bids.xsl` — 6/6,
`notifications.xsl` — 6/6.

**Найдено и исправлено.** На трёх витринах — `usps.online-spb.com`,
`fedex.online-spb.com`, `localhost` — `policy.xsl` (страница товара)
была старой, короткой версией (1217 строк против 1609) и вовсе не
содержала форм `do_offer` и `do_bid`: покупатель не мог ни предложить
цену, ни сделать ставку, хотя контроллеры и XML (`show_offer`,
`show_action`, `offerAmount`, `actionBitAmount`, `actionMaxBitAmount`
из `ProductInfo.jsp`) всё это отдают. Блок из `dhl.online-spb.com/policy.xsl`
(строки 823–864: форма предложения под `show_offer = 'true'` и форма
ставки с текущим максимумом под `show_action = 'true'`) вставлен перед
формой «в корзину» во все три шаблона (`localhost` — cp1251, кодировка
сохранена). Все три перепроверены на well-formed XML. Мобильные
`policy.xsl` не трогались (другая разметка, там этих форм нет ни на одном
сайте).

**Замечено, не исправлено.** `OrderAction.addOrder` помечен
`@PutActionRequestMapping(action = "add")`, но все формы «в корзину»
отправляют POST, а браузерная форма PUT послать не может — аннотированный

это тот же код). То есть `addOrder` — мёртвый дубликат. Менять аннотацию
на `@Post` не стала: тогда `addOrder` перехватил бы запрос вместо
`doPost`, а он не вызывает `response()` и не готовит бины страницы так,
как `doGet`. Правильный шаг — удалить `addOrder` либо доделать его до
полноценного обработчика вместе с `prepareOrder()` (см. план по
`OrderAction`).

## О «лучших практиках»: почему массовая модернизация не применялась вслепую

Сборка в этом окружении невозможна (нет `javac`/`mvn`, нет сети), вся
проверка — статическая. Массовая автозамена без компилятора — это риск молча
изменить поведение. Поэтому вместо «косметики на 570 мест» ниже — безопасный,
поэтапный план, который выполняется под компилятором и тестами:

1. **Логирование вместо `System.out`/`printStackTrace`.** ~570 `System.out`/
   `System.err` и `printStackTrace` в 49 файлах. В 158 классах логгер уже
   есть — там замена на `log.error(msg, e)` тривиальна и делается первой.
   Практика Jakarta EE: SLF4J/Log4j2, никакого вывода в stdout из
   веб-приложения.
2. **Дженерики и современные коллекции.** ~263 `Vector`/`Hashtable`/
   `StringBuffer` и ~563 сырых `ArrayList`/`HashMap` без типов. Менять по
   пакету: `Vector`→`ArrayList`, `Hashtable`→`HashMap`, `StringBuffer`→
   `StringBuilder`, проставить параметры типов. Каждый пакет — отдельная
   компиляция.
3. **JDBC и пул соединений.** 32 места с `Class.forName`/
   `DriverManager.getConnection`. Практика Jakarta EE: `DataSource` через
   JNDI (`@Resource`), пул контейнера, `try-with-resources` на
   `Connection`/`Statement`/`ResultSet`. Это же закроет утечки соединений,
   отмеченные в прошлых проходах.
4. **Хеширование паролей** (отложенный п. 1) — BCrypt/Argon2 + миграция
   схемы; убрать копирование пароля в связанную админ-запись и отправку
   пароля письмом.
5. **DAO/сервисный слой.** Гигантские `*Bean` с SQL внутри разнести на
   тонкие бины представления и DAO; параметризовать оставшиеся ~760
   конкатенаций SQL.
6. **Прочее из бэклога** (см. разделы выше): извлечь `prepareOrder()` и
   убрать мёртвый `addOrder`; форма ввода трек-номера для перевозчика;
   изменение статуса спора оператором центра; генерация id критериев через
   `one_sequences` вместо `MAX(id)+1`; whitelist расширений загрузки.

Ни одно из этого не применялось «пакетно» именно потому, что без сборки
нельзя гарантировать отсутствие регрессий; всё перечислено как проверяемый
план работ.

# Проход 22 — журналирование latency (медленные запросы и методы)

**Было.** perf4j присутствовал только как импорт аннотации `@Profiled` в трёх
классах — реальных замеров нигде не было. Поле `sqltime` в
`QueryManagerHibernate` не использовалось. Узнать, что метод или SQL тормозит
(например, из‑за отсутствующего индекса), было невозможно.

**Сделано** — замер в двух центральных точках, через которые проходит всё:

1. Новый класс `com.cbsinc.cms.utils.Latency`. Если вызов длится дольше
   порога, в лог пишется **WARN с исключением** (`SlowSqlException` /
   `SlowMethodException`, никогда не выбрасываются — только логируются, чтобы
   в журнале была строка «где, сколько мс, какой запрос» и стек вызовов,
   ровно как у ошибки). Пороги — системные свойства JVM, без пересборки:
   `-Dcms.latency.sql.ms=1000`, `-Dcms.latency.method.ms=1000`
   (по умолчанию 1 секунда). Ниже порога — `DEBUG` с временем.
2. `QueryManagerHibernate`: все **13** методов `execute*` обёрнуты в
   `try/finally` с `Latency.sql("QueryManagerHibernate.<метод>/<арность>",
   start, query)`. Это покрывает все ~2 000 обращений к БД по коду разом; в
   сообщении — текст запроса (обрезан до 600 символов), чтобы сразу видеть,
   какому запросу нужен индекс.
3. `FrontControllers`: диспетчеризация контроллера (аннотированный action
   или `doGet`/`doPost`) обёрнута в `try/finally` с
   `Latency.method("<Контроллер> <HTTP-метод> action=<action> <URI>", start)`
   — медленный метод контроллера виден вместе с URL и action.

Пример строки в логе:
```
WARN  Latency - slow sql
com.cbsinc.cms.utils.Latency$SlowSqlException: SLOW SQL 2384 ms (threshold 1000 ms)
  in QueryManagerHibernate.executeQueryWithArgs/2 - check indexes / execution plan:
  select ... from soft where site_id = ? and name like ? ...
	at com.cbsinc.cms.QueryManagerHibernate.executeQueryWithArgs(...)
	at com.cbsinc.cms.ProductlistBean.search(...)
```

Диагностика медленного запроса: взять текст из сообщения, выполнить
`EXPLAIN <запрос>` в MySQL и добавить индекс по колонкам из `WHERE`/`JOIN`.

Проверено статически: баланс скобок, отсутствие затенения параметра `query`
локальными переменными (`finally` ссылается именно на параметр), ранние
`return` внутри методов корректно проходят через `finally`.

Не сделано: замер внутри `QueryManagerSQL`/`QueryManager_last` (по коду они
не используются контроллерами; при необходимости — тот же приём).

# Проход 25 — `Statement` → `PreparedStatement`: разбор и первая партия (`OrderFaced`)

**Разбор.** В `QueryManagerSQL` два семейства методов: `*WithArgs` уже
используют `PreparedStatement` с параметрами; методы без аргументов
(`executeQuery(query)`, `executeQueryList(query)`, `executeUpdate(query)`)
гонят готовую строку через голый `Statement`. Безопасность каждого вызова
зависит от того, что склеено в строку вызывающим кодом. Статический разбор
всех 1 084 вызовов «без аргументов»: 821 — `CreateShopBean` и сам менеджер
(шаблонные вставки, литералы), 221 — склейка только внутренних значений,
**42** — склейка значений, приходящих из запроса/бинов. Из них
`AuthorizationPageFaced` (6) — ложные срабатывания: cookie проходит через
`hashCode()` и в SQL попадает число. Остальные 36 — в основном числовые id из
бинов; формально требуют параметризации.

**Почему нельзя «просто заменить `Statement` на `PreparedStatement`» внутри
менеджера:** уже склеенная строка без `?` не получает никакой защиты.
Переписывается вызывающий код — данные выносятся в `?` и передаются через
`*WithArgs`.

**Сделано — `OrderFaced.java` (14 участков):**
- 8 вызовов через голый `Statement` переведены на `executeQueryWithArgs` /
  `executeInsertWithArgs` / `executeUpdateWithArgs`: три `select … from orders
  where order_id = ?`, `count(...)` по заказу, два `select currency_id from
  account where user_id = ?`, `UPDATE account SET amount = ? WHERE user_id = ?`
  и самый крупный — `insert into account_hist` (18 колонок, ранее целиком
  склейкой) — теперь 13 связанных параметров, порядок сверен с колонками.
- 6 «наполовину параметризованных» UPDATE (значения через `?`, но
  `where order_id = " + getOrder_id()`) — условие тоже переведено на `?`,
  `order_id`/`user_id` добавлены в `args` (механизм связывает по имени поля,
  как в `FDResponceAction`).
- Добавлен `import java.util.HashMap`. Типы: id/суммы из бинов — `String`
  (MySQL приводит к числу, как и раньше), вычисленные значения — `Float`.

# Проход 26 — постраничная загрузка списков (защита от OutOfMemory)

**Аудит.** Проверено, как списочные методы грузят данные и связаны ли они с
пагинацией в интерфейсе. Ключевые находки:

- **`ProductlistFaced` уже постраничный.** Главный список товаров (строки
  2018, 2541) грузится через `executeQueryList(query, limitProductList,
  productlistBean.getOffset())`; все вспомогательные блоки главной страницы
  (новинки, офферы, отзывы, аукционы) — с лимитами. `getQuantityProducts` /
  `getQuantitySearch` намеренно грузят полный счётчик через `getRowCount()`
  для подсчёта числа страниц — **их трогать нельзя**.
- **29 вызовов `executeQueryList(query)` в `ProductlistFaced`** — это блоки
  карточки одного товара (колонки, вкладки, файлы, отзывы), привязанные к
  одному `tree_id`+`site_id`, ограниченные по смыслу; пагинации у них нет и
  не требуется.
- Механизм пагинации в `QueryManagerSQL`: `executeQueryList(query, limit,
  offset)` и `executeQueryWithArgsList(...)` выполняют запрос, делают
  `rs.absolute(offset)` и читают в память только `limit` строк — то есть
  вся таблица в Java-память не грузится.

**Исправлено — `CreteriaListBean` и `Creteria_listBean` (3 запроса).**
Списки-справочники критериев грузились через `executeQueryList(query)` с
`limit 10 offset N`, **зашитыми прямо в текст SQL**. Переведены на
`executeQueryWithArgsList(query, new Object[] { link_id }, 10, offset)`:
`link_id` вынесен в параметр, лимит и offset передаются методу. Важное:
изначально ошибочно оставил `LIMIT ? OFFSET ?` в SQL *и* передал их методу —
метод сам делает `rs.absolute(offset)`, offset применился бы дважды; поймано
до сборки, `LIMIT/OFFSET` из текста убран.

**Маппинг интерфейс → метод подтверждён.** У бинов есть `setOffset`, они сами
строят навигацию `Creteria.jsp?offset=+10/-10`, которая выводится ссылками
«вперёд/назад» в таблице (строки 182, 204). Цикл замкнут: клик по странице →
`offset` в бин → `LIMIT/OFFSET` в загрузке.

**Замечание о нагрузке на БД (в бэклог).** Текущий механизм защищает
Java-память, но запрос уходит в MySQL без `LIMIT`, поэтому СУБД всё равно
строит полную выборку и курсор перематывается на стороне драйвера.
«Настоящая» постраничность — `LIMIT ? OFFSET ?` в самом SQL плюс отдельный
`COUNT(*)` для числа страниц — более крупная переделка, выполнять под
компилятором и тестами.

# Проход 29 — хеширование паролей и безопасное восстановление

**Было.** `tuser.passwd` хранился открытым текстом; логин сравнивал пароль
прямо в SQL (`login = ? and passwd = ?`); «забыл пароль» высылал пароль на
почту; регистрация и создание сайта (`CreateShopBean`, 20 INSERT-ов) писали
пароль как есть.

**Решение.** Новый `com.cbsinc.cms.utils.PasswordHash` — PBKDF2-HMAC-SHA256,
120 000 итераций, 16-байтовая соль, формат `pbkdf2$iter$salt$hash`. Выбран
PBKDF2 из стандартного JDK, а не bcrypt: добавить внешнюю зависимость без
компилятора и сети нельзя проверить. Сравнение в константное время.

**Изменения.**
- `AuthorizationPageFaced.isLoginCorrect(login, passwd, …)`: выборка по
  `login` + `site_id` без пароля, проверка `PasswordHash.matches` в Java.
  **Прозрачная миграция**: старый открытый пароль принимается и тут же
  перезаписывается хешем (`UPDATE tuser set passwd = ?`). В бин кладётся
  введённый пароль, а не значение из БД (контроллеры повторно логинят при
  смене сайта).
- Регистрация (`isRegCorrect`): поиск существующего аккаунта по `login`
  (по хешу искать нельзя), `passwd` хешируется в UPDATE и INSERT.
- `CreateShopBean`: все 20 INSERT в `tuser` (пользователь, гость, служебный
  админ) и копирование пароля владельца в админ-запись — через `hash()`.
- `SendPassword`: пароль восстановить нельзя — генерируется временный
  (12 символов, `generateTemporary()`), его хеш сохраняется в `tuser`,
  на почту уходит временный. Шаблон письма `password.txt` / `@Password`
  не менялся.

**Компромисс (осознанный).** Вход по cookie и поиск админа загружают бин
из БД, и он держит **хеш**; последующий повторный `isLoginCorrect` при смене
сайта передаёт этот хеш. Чтобы не сломать сценарий, `isLoginCorrect` также
принимает значение, совпадающее с хранимым хешем (`passwdIsStoredHash`).
Это «pass-the-hash» при утечке БД — но утечка БД уже даёт подделку
`idsession`-cookie. Правильный следующий шаг — переавторизация по `user_id`
без пароля вообще. Пароль в сессии (`AuthorizationPageBean.strPasswd`) —
прежнее поведение, теперь используется также `getEmailPassword()`.

**Миграция схемы не требуется**: хеш укладывается в текстовую колонку
`passwd` (проверить длину ≥ 100 символов; при `VARCHAR(50)` —
`ALTER TABLE tuser MODIFY passwd VARCHAR(255)`). Письма «@Password» при
создании сайта (ProductlistAction/DeployDesign/Search) отправляют пароль
владельца в момент создания — это поведение продукта, отмечено в бэклог.

# Проход 31 — постраничность на уровне SQL (устойчивость к нагрузке)

**Было.** Три постраничных метода `QueryManagerSQL` (`executeQueryWithArgs`,
`executeQueryWithArgsList`, `executeQueryList` с `limit/offset`) отправляли
запрос в MySQL **без** `LIMIT`, открывали `TYPE_SCROLL_SENSITIVE` курсор и
делали `rs.absolute(offset)`: сервер БД материализовал полную выборку, а
драйвер перематывал её. Java-память была защищена (проход 26), база — нет.
Счётчики `getQuantityProducts`/`getQuantitySearch` грузили всю выборку в
память только ради `getRowCount()`.

**Исправлено.**
- Новый `QueryManagerSQL.pageQuery(query, limit, offset)`: срезает
  завершающие `;` и дописывает `LIMIT <limit> OFFSET <offset>`. Оба значения —
  `int` из кода (лимиты из `appconfig.property`, offset распарсен из
  `?offset=` в число), поэтому конкатенация чисел безопасна. Отрицательный
  лимит = «без лимита» (обратная совместимость).
- Во всех трёх методах убран `rs.absolute(offset)`, курсоры переведены с
  `TYPE_SCROLL_SENSITIVE` на `TYPE_FORWARD_ONLY`. Семантика та же:
  `absolute(offset)`+`next()` пропускал ровно `offset` строк — как `OFFSET`.
  Java-цикл `limmit--` оставлен как страховка.
- `ProductlistFaced.getQuantityProducts`/`getQuantitySearch`: вместо
  выполнения полного запроса — `SELECT COUNT(*) FROM ( <query> ) AS cnt_q`.
  Интерфейс не менялся: `allFoundProducts` заполняется тем же числом.

**Проверено.** Ни один вызывающий не передаёт в постраничные методы запрос,
уже содержащий `LIMIT` (старые `limit` в тексте закомментированы). Оставшиеся
`executeQueryList(query)` + `getRowCount()` в `ProductlistFaced` — блоки одной
карточки товара (≤ десятки строк по `tree_id`), не требуют пагинации.

**Для теста.** Главная витрина, поиск, разделы каталога: число «всего
найдено» и переходы `?offset=` должны совпадать с прежними; в логе MySQL
запросы теперь заканчиваются `LIMIT n OFFSET m`. Проверить нагрузочно на
крупном каталоге.

# Проход 40 — переименование всех переменных и методов в camelCase (весь проект)

По запросу пользователя: **все переменные и методы во всём проекте** приведены
к camelCase, включая синхронные правки JSP/EL и JS, чтобы автоматическая
привязка полей форм (`jsp:setProperty property="*"`) и явные
`jsp:getProperty`/`jsp:setProperty` не сломались молча в рантайме (javac их не
проверяет). XSL-шаблоны не тронуты: они работают с уже сгенерированным XML, а
не с именами Java-свойств.

## Методология
1. Построен словарь переименования из 1097 реально используемых
   snake_case-идентификаторов Java-кода (поля, методы, локальные переменные) —
   собраны **только вне строковых литералов и комментариев** (символьный
   разбор кода посимвольно, с корректной обработкой экранирования), чтобы SQL,
   зашитый в строки, не пострадал.
2. Конверсия `snake_case` → `camelCase` (например `site_id` → `siteId`,
   `getCatalog_id` → `getCatalogId`, `creteria1_id` → `creteria1Id`).
3. Проверены 9 коллизий целевых имён (например `strShow_action` /
   `strShow_Action` → `strShowAction`) — все относятся к разным классам,
   конфликтов компиляции не создают.
4. Применено к 327 Java-файлам (src + test): 182 файла затронуты, 18382
   переименования идентификаторов.
5. JSP (120 файлов): переименование внутри `<% %>`/`<%= %>` — также посимвольно
   вне строк/комментариев, плюс отдельное безопасное правило: строковый
   литерал, полностью совпадающий с одним идентификатором (например
   `"creteria1_id"` как имя поля формы), переименовывается, а SQL-фрагменты
   (всегда содержат пробелы/ключевые слова) — никогда, так как под правило не
   попадают. Плюс явные `property="X"` в `jsp:getProperty`/`setProperty` (60
   переименований).
6. Каскад по HTTP-параметрам для 14 форм с `property="*"` (автопривязка по
   имени параметра): синхронно переименованы `request.getParameter("X")` в
   Java (1621 мест, 62 файла), атрибуты `name=`/`id=` и `getElementById` в JSP
   (270 мест, 50 файлов), а также отдельные `.js`-файлы и инлайновый
   `<script>` внутри самих JSP через `document.all[...]`/`getElementById`/
   `getElementsByName`/`.elements[...]` (909 + 950 мест).

## Найденные и исправленные баги в процессе
- **Дублирующийся метод после нормализации имён**: в `AuthorizationPageBean`
  существовали два независимых (уже до переименования!) геттера/сеттера
  `getCatalogParent_id()`/`setCatalogParent_id(long)` (основные) и
  `@Deprecated getCatalog_parent_id()`/`setCatalog_parent_id(long)` (мёртвый
  дубликат) — после camelCase оба стали `getCatalogParentId()` и вызвали
  ошибку компиляции "already defined". Мёртвый `@Deprecated`-дубликат удалён.
- **Самостоятельно найденный и исправленный баг переименования**: первая
  версия скрипта для JSP-скриптлетов заменяла идентификаторы по всему тексту
  `<% %>`, не пропуская строковые литералы — из-за этого в 90 файлах
  испортились SQL-запросы, зашитые прямо в JSP (например,
  `"select creteria1_id ... from creteria1 ..."` превратилось в
  `creteria1Id`, что не совпадает с реальным именем колонки в БД). Обнаружено
  до сборки поставки; JSP и связанные `.js` полностью откачены к pristine-
  версии и переименование переделано с корректным посимвольным разбором строк.
  Финальная проверка: 341 SQL-подобная строка в JSP и 2327 в Java — ни одна не
  повреждена (перепроверено отдельным скриптом с честным посимвольным разбором
  строк/эскейпов, без ложных срабатываний от предыдущей наивной проверки).

## Проверка

## Проверка прохода 41 (по запросу "double check more") — откат каскада по HTTP-параметрам

**Главная находка: мой каскад переименования HTTP-параметров был ошибкой и
ломал приложение.** В проходе 40 я переименовал ключи `request.getParameter("catalog_id")`

а `StripeReturnServlet` стал читать `getParameter("sessionId")` → возврат после
оплаты не работал бы. Ещё один эффект: глобальный фильтр `rejectNonNumericIds`

суффиксом `_id` — camelCase-параметры (`catalogId`) проходили бы мимо него.

  запроса со свойством только при **точном** совпадении имён, а имена свойств
  теперь camelCase. Сразу после каждого wildcard добавлены явные строки
  `<jsp:setProperty name="..." property="siteId" param="site_id"/>` — по одной на
  каждое переименованное свойство бина (586 строк на 14 файлов, список сеттеров
  взят из исходной версии класса, чтобы имена параметров были точными).
