# Роли доступа CMS-Manhattan: как это устроено и что проверено

## 1. Где живут роли

Роль — это одно число `tuser.levelup_cd`, которое при входе копируется в
`AuthorizationPageBean.roleId` (до прохода 1 поле называлось `intLevelUp`).
Словарь ролей в БД (`sql/init.sql`, таблица `roles`) и константы в Java
(`controllers/SiteRole.java`):

| Код | БД `roles.NAME` | Java `SiteRole` | Используется в коде |
|---|---|---|---|
| 0 | Guest | `GUEST_ROLE_ID`, логин `GUEST = "user"`, `GUEST_ID = 1` | да |
| 1 | Menmber *(sic)* | `MEMBER_ROLE_ID` | да |
| 2 | Administrator | `ADMINISTRATOR_ID` = `ADMINISTRATOR_ROLE_ID` | да |
| 3 | Shipping | `SHIPPING_ROLE_ID` (проход 33) | обработка заказов сайта: просмотр, смена статусов |
| 4 | Fullfilment | `FULFILLMENT_ROLE_ID` (проход 33) | обработка заказов сайта: просмотр, смена статусов |

Роли 3 и 4 объявлены в БД и в Java под **разными именами** (БД: перевозчик и
фулфилмент, Java: контент-менеджер и покупатель) и нигде не проверяются.
Фактически система трёхуровневая: 0 / 1 / 2. Перевозчик и центр разрешения
споров (проходы 4, 5, 11) определяются **не ролью**, а тем, что текущий сайт
указан в `shipping_company.site_id` / `resolution_center.site_id`.

## 2. Ключевой принцип: учётная запись привязана к сайту

`tuser` хранит `site_id`, и **все** запросы входа (`AuthorizationPageFaced.isLoginCorrect`,
восстановление по cookie `session_id`) ищут пару логин/пароль **только в
пределах текущего сайта**. Одна и та же пара на другом сайте — это другая
строка `tuser` (или её нет — тогда посетитель становится гостем).
Отсюда следует всё остальное:

- **Гость (0).** `FrontControllers` при первом заходе выставляет
  `login = "user"`, `roleId = 0`, `intUserID = 1`. У каждого сайта есть своя
  строка `tuser` «user/user» (создаётся вместе с сайтом, `CreateShopBean`).
  Гость видит каталог, товар, поиск, может положить в корзину; создать сайт,
  удалять/поднимать/раскрашивать позиции, публиковать карточки — нет.
- **Зарегистрированный пользователь (1).** `RegistrationAction` пишет
  `levelup_cd = 1` и `site_id` = сайт, на котором регистрировался; создаётся
  счёт (`account`). Может: заказ, оплата, предложения цены, ставки, отзывы,
  подписка на товар, уведомления, а также свои «пользовательские» карточки
  (`ProductUserPost*`, `Co1/Co2…PostUser`, `Ext*…PostUser` — у них проверка
  только `roleId != 0`), **создать собственный сайт** (`action=create_site`).
  Удалять/переставлять позиции — только свои: если `roleId != 2`, контроллер
  сравнивает `getIntUserID()` с владельцем товара (`getWhoseProduct`).
- **Администратор (2).** Полный доступ к контенту **своего сайта**: карточки
  каталога (`ProductPostCre`, `NewArrival`, `NewBlock`, `SponsoredBySellers`,
  `Recommented`, `SiteDesign`, `BottomList`, `FooterLinks`, `Ext*`,
  `ProductInfo*` — проверка `roleId != 2`), критерии (`Creteria*.jsp`),
  загрузки (`AuthFilter`, `minAccessLevel` = 1 пропускает и членов — это
  нужно продавцам), заказы без проверки баланса (`OrderAction`: `roleId != 2
  && balans < amount`), удаление любого товара **этого же сайта**
  (`getSite_id().compareTo(getSiteByProduct(...))`).

**Глобального супер-администратора нет.** Администратор главного сайта не
может править другие сайты: у него нет строки `tuser` на них, и при
переключении `?site=N` `isLoginCorrect` не найдёт его — сессия станет
гостевой (ветка `else { setStrLogin(GUEST) … }` в `loginUserSite`). Если такой
доступ нужен по замыслу — это отдельная доработка (см. §5).

## 3. «Пользователь создаёт свой сайт → появляется его связанная админ-запись»

Реализовано ровно так. `ProductlistAction.createSite` / `createSiteById`
(`CreateShopBean.addShop*`):

1. Гость (`roleId == 0`) отклоняется («you_can_not_to_create_shop»); член (1)
   и администратор (2) — могут.
2. Создаётся строка `site` с `owner = user_id` создателя.
3. В `tuser` вставляются **две** строки для нового `site_id`: копия логина и
   пароля создателя с `levelup_cd = ADMINISTRATOR_ID (2)` — это и есть
   связанная админ-запись — и гостевая `user/user` с `levelup_cd = 0`.
4. `AuthorizationPageFaced` ищет `select site_id from site where owner =
   user_id` → `user_site`; кнопка `action=login_usersite` переключает
   `site_id` на свой сайт и повторно проверяет тот же логин/пароль —
   пользователь оказывается администратором своего сайта. На его сайте
   регистрируются свои пользователи (обычные `levelup_cd = 1`, `site_id` =
   его сайт) — изолированно от главного сайта.

Нюансы: пароль **копируется** (при смене пароля на одном сайте второй не
меняется); `user_site` берёт **последний** созданный сайт (`order by site_id
desc`), так что при нескольких сайтах кнопка ведёт только на новейший.

## 4. Что было сломано и исправлено в этом проходе

**Проверки роли не останавливали выполнение.** Схема во всех контроллерах
карточек: `doPost` → `action(request, response, servletContext)` (читает поля,
при `roleId != 2` делает `sendRedirect("Authorization.jsp")`, но **без
`return`**) → и тут же `insertRow/updateRow/saveDescSoft`. Итог: член или
гость отправлял `POST …Post.jsp` с `action=save` — редирект уходил, но строка
всё равно записывалась. В проходе 7 это было закрыто в 5 файлах; теперь
после каждого вызова `action(...)` в `doGet`/`doPost` стоит
`if (response.isCommitted()) return;` — **83 места в 43 контроллерах**.

То же в семействе `Productlist*` (`ProductlistAction`, `ProductlistMarketPlaceAction`,
`DeployDesignAction`, `SearchAction`): в `deletePosition` / `upPosition` /
`colorPosition` гость получал `forward` на `Authorization.jsp`, а не-владелец
— сообщение «You must be owner», после чего код шёл дальше и удалял или
переставлял чужой товар того же сайта. После каждого такого `forward` теперь
`return true` (ответ уже отправлен).

Оба исправления проверены: баланс скобок и локальные переменные во всех 47
затронутых файлах.

## 5. Что осталось (не менялось)

1. Роли 3/4 — расхождение имён БД ↔ Java и полное отсутствие использования.
   Либо убрать, либо задействовать для перевозчика/центра споров вместо
   проверки по `shipping_company.site_id`.
2. Нет супер-администратора «на все сайты». Простейший вариант: константа
   `SUPERUSER_ROLE_ID = 5`, и в `isLoginCorrect` при `?site=N` разрешать
   вход по строке главного сайта, если там `levelup_cd = 5`; в проверках
   владельца — `roleId >= 2`.
3. Единичные контроллеры с проверкой только «не гость» для админских
   операций: `Co1/Co2ProductPostUserAction`, `ProductReviewPostAction`
   (админ не может писать отзывы — `roleId == 2` блокируется намеренно?).
4. Пароли в открытом виде и их копирование в связанную админ-запись
   (см. `FIXES.md`, отложенный п. 1).
5. `AuthFilter` защищает только 20 URL из `web.xml`; JSP карточек
   (`*Post.jsp`) на него не завязаны — их защита целиком в контроллерах,
   что и делает п. 4 критичным.

## 6. Проход 33 — операционные роли 3 и 4

Роли оформлены как **персонал склада** своего сайта. В `SiteRole` добавлены
`SHIPPING_ROLE_ID = 3`, `FULFILLMENT_ROLE_ID = 4` и статические проверки
`isAdministrator(roleId)`, `isStaff(roleId)` (2, 3, 4),
`canProcessOrders(roleId)`; старые неиспользуемые `CONTENT_MANAGER_ID` /
`CUSTOMER_ID` удалены.

Что может персонал (3, 4):
- видеть все заказы **своего** сайта (список по дате и поиск по статусу);
- открывать любой заказ сайта и менять его платёжный / доставочный статус
  (селекты в `order.xsl` открыты ролям 2/3/4).

Чего не может: менять состав, адрес и суммы заказа, оформлять (`save`)
чужой заказ, трогать товары, цены, деньги, пользователей — всё это остаётся
только у администратора (2). Кросс-сайтового доступа нет: чужой сайт → отказ.

Смена статуса персоналом и администратором на **чужом** заказе идёт через
новый `OrderFaced.setStatusOnly()` — без перезаписи `orders.user_id`, без
списания с баланса.
